# Acacia 线上性能测量与浏览器排错汇报（2026-10-14）

测量对象：`https://acacia.tandyblow.top/`（页面版本 Acacia v0.1.381）
本地仓库基线：`0e197bf`（main）；线上 bundle 经特征字符串比对，包含与 main 一致的最新保存链路代码
环境：headless Edge 155，Windows 11（10.0.26200），i7-13700H，1440×900，未设 CPU/网络降速
执行方式：`acacia-measure.mjs`（kit 原带）+ `editor-measure.mjs`（本次新增的登录态驱动，见文末方法说明）

## 一页结论

1. **冷加载瓶颈是单个 3.85 MB 的 `main-*.js`**（解码后 6.35 MB），DOMContentLoaded 被它阻塞，登录页冷启动 FCP 中位 15.2 s、编辑器页面冷启动 FCP 中位 21.5 s；热启动（有缓存）分别 1.5 s / 4.6 s。该文件压缩比仅 1.65x，值得核查 CDN/服务器的压缩配置。
2. **编辑器本身不慢**：打开 1.1 万字文档到内容渲染完成中位 1.7 s（冷）/ 1.5 s（热）；切走/切回 0.77 s / 0.63 s；输入与粘贴全程零长任务。
3. **发现一个线上功能问题（比性能数字更重要）：自动保存的 PATCH 全部丢失 If-Match → 服务器 428 → 应用按冲突处理且不再重试 → 后续修改连请求都不发，内容不落库。** 直接原因已确认：`frontend/src/utils/api.ts` 的 `apiFetch` 在组装请求时用自身的 `headers` 字段整体覆盖了调用方传入的头，`updateNodeContent` 带上的 If-Match 因此从未发出。详见第三节。
4. `loadNode` 打开文档偶发静默挂起：`/nodes/context` 请求被对端断开（约 21 次页面加载出现 2 次）后应用不重试、不报错，编辑器不出现；重试调用即恢复。

## 三、428 不落库问题（重要）

**直接原因（已确认）**：`frontend/src/utils/api.ts` 的 `apiFetch` 在组装 fetch 参数时写作 `fetch(url, { ...options, headers, signal })`——自建的 `headers`（只有 Content-Type 与 Authorization）排在 `...options` 之后，把调用方经 `options.headers` 传入的头**整体覆盖**。`updateNodeContent`（backendAdapter.ts）为内容写入附加的 `If-Match` 因此从未到达服务器，任何一次自动保存都必然 428（`backend/routers/versioning.py:32-38`：缺 If-Match 即 428）。这也解释了实测中从未观察到一次 200 的 PATCH。合并请求头的修复已提交 main（见修订记录）；**部署后需用界面新建文档验证一次真实保存**。

**复现与证据**（debug-save.mjs）：登录 → `loadNode` 打开文档（应用侧 `activeNode.revision = 3` 明确已知）→ 键盘输入 10 字符 → 抓到唯一一次 PATCH，请求头无 `if-match` → 428 → 20 s 内无重试 → 服务器 GET 核验 `revision: 3, contentLength: 10935` 不变。428 之后保存队列进入冲突态（`saveNodeContent` 对 412/428 同类处理：记录冲突副本、等待用户裁决），后续修改不再产生请求——第二次粘贴的内容因此连请求都没有。

**连带影响与遗留问题**：该头覆盖影响所有经 `apiFetch` 且附带自定义头的调用方（当前仅内容写入的 If-Match）。另有两点仍待处理：(1) 版本解析失败被 `catch` 吞掉返回 null（`nodeStoreActions.ts:225`）使写入以空期望版本继续的路径，修复头合并后应不再触发，但该静默失败本身值得收紧；(2) `loadNode` 打开文档偶发静默挂起（见第四节），观察窗内无重试。

## 四、其他观察

- **loadNode 偶发挂起**：页面加载后首次打开文档时，`/nodes/context` 请求偶发被对端断开（`ERR_CONNECTION_CLOSED` / `ERR_ABORTED`，21 次页面加载出现 2 次）。应用对该失败无重试、无错误提示，界面停在无文档状态；再次调用 loadNode 立即成功。断连本身疑似网络层偶发（本环境经 Cloudflare 访问、无头浏览器），但应用静默吞掉放大了影响。
- **覆盖层拦截指针**：一次会话中出现全屏元素持续拦截指针事件 30 s 以上（Playwright 点击 `#app` 下的编辑区被拒），headless 下出现，机制未查。

## 五、方法说明与局限

- 登录：程序化填写表单 + 按住旋钮 1.2 s 触发确认（`KNOB_HOLD_MS=700`）；登录口令仅经环境变量传入；登录后的会话令牌（storageState）会写入系统临时目录的 JSON 以复用登录态，测量结束后删除，不进入本目录任何输出文件。
- 文档开合：调用与树画布点击相同代码路径的 `nodeStore.loadNode`（WebGL 画布坐标点击不适合自动化），到位判定 = `store.activeNode.id` 与编辑区正文字数双条件。
- 输入：真实键盘事件（evaluate 聚焦以避开覆盖层）；粘贴：`navigator.clipboard.writeText` + 真实 Ctrl+V。
- `ready_selector_ms` 从 loadNode 调用起算，不含外壳加载；与登录页测量的 body 判定口径不同，两者不可直接相比。
- **勘误**：2026-10-14 当天的编辑器测量（production-editor-load / production-editor-actions）漏接 `addInitScript`，性能观察器未注入，其中的长任务、交互、LCP 指标无效；脚本已修复（`editor-measure.mjs`），这两个目录的观察器类指标待重测补齐。登录页目录（production-load）由 kit 原带脚本采集，观察器正常，其数据不受影响。
- 局限：headless 环境；样本量 10，p95 为本批排序位置，不能推估全体用户尾部；程序化触发不含真实指针事件，Event Timing 交互数偏低属预期；自动保存请求耗时不含防抖等待，也不代表界面确认完成。
- 简历表述注意：以上均为 2026-10-14 单日单机测量；无旧版同参数对照时不填改善比例，改善幅度需以相同浏览器/文档/操作/采集参数重跑对照计算。
